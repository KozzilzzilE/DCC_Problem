### 절대 준수 제약 (검토 시 우선 확인 항목)

1. **증상 판정 임계값 `0.5` 고정 및 `force_top1=False`:** 9개 클래스 모두 `sigmoid 확률 >= 0.5`만 출력하며, `0.5` 미만일 때는 빈 리스트(`[]`)를 허용한다. 클래스별 임계값이나 `maxent/expected` 개수 규칙을 제출 판정에 쓰지 않는다.
2. **미래 정보 사용 금지:** 4-1·4-2 모두 현재 시점까지 도착한 발화의 `text`, `speaker`, `start_ms`, `end_ms`만 사용할 수 있으며, 통화의 총 발화 수나 총 통화 시간을 입력으로 쓸 수 없다.
3. **공식 `Validation` (`3,640`통화) 개발 중 사용 금지:** 현재까지 아래에 보고하는 모든 비교·선정 수치는 `Training` 내부 분할인 **`Dev 2,920`통화 (`87,814`시점)** 기반 개발 재검증 결과다. 공식 `Validation`은 최종 구성이 완전히 동결된 뒤 단 1회만 확인하는 용도다.

## 2. 배경 및 기존 베이스라인(`mission4-streaming`)과의 연결 구조

본선 정량 평가는 **4-1 (매 발화 시점 평균 Jaccard)** 과 **4-2 (중단 시점 `Macro-F1 × 평균 조기판단력`)**, 정성 평가는 **과정 논리성·문제 해결 절차·팀 협업**을 종합한다.

### 기존 팀원 베이스라인 상태 (`ENS3 + E026`)
- **분류기 앙상블 `ENS3` (`E001` 전체 통화 + `E002/E007` 균등 앞부분 누적 학습, 모두 TAPT `klue/roberta-base`):**
  - `Dev 2,920` (`raw p >= 0.5`, Top-1 없음): `4-1 = 0.506001` (`E002` 단독 `0.502733`), `4-2 C0 (β=0) = 0.498835`.
- **학습형 중단 정책 `E026` (`v(t) + 128·δ̂(t) >= 0.5`, 최소 5발화):**
  - `Dev 2,920` `4-2 = 0.503146` (`Macro-F1 0.6064 × 조기판단력 0.8298`, 내부 대조 `0.498953` 대비 `+0.004193`).

### 연결 과정에서 도출한 3가지 빈틈과 역할 분담
1. **빈틈 ① (미션 4-1 오류 원인과 손실함수 불일치 — 사용자 담당 해결):**
   - `BCE`로만 학습된 기존 모델은 초반에 `0.5`를 넘기지 못하는 **빈 예측률(`15.15%~16.43%`)** 이 높고, 4-1 공식 채점식인 **시점별 집합 Jaccard**와 목적함수가 직접 정렬되어 있지 않았다.
2. **빈틈 ② (미션 4-2 `E026`의 누수 논란·`Macro-F1` 하락·신뢰구간 미달 — 사용자 담당 해결):**
   - 기존 `E026`은 확률 보정값 `logit_shift`에 `Dev 2,920`을 포함한 `29,200`통화 라벨 통계(`E016_final/shift`)를 사용해 `Dev` 라벨 간접 유입 논란이 있었다.
   - `Dev`에서 `Macro-F1`이 대조(`0.6137`) 대비 `0.6064`로 떨어졌고, 아직 `raw p >= 0.5` 증상이 0개(빈 예측 `[]`)인 상태에서도 중단하는 통화(`43`건: 중간 조기 중단 `27`건 + 마지막 도달 `16`건)가 있었으며, 95% 신뢰구간 하한이 음수였다 (`wide/result.json` `1,000`회 `seed=2026`: `[-0.000893, +0.009200]`; 동일 입력 재생 `10,000`회 `seed=20261116`: `[-0.001003, +0.009525]`).
   - 공유 패키지에는 `E011_oof` (`fit 26,280` 5겹 교차 확률표) 실물이 빠져 `fit-only` 정책 재학습·검증이 불가능한 상태였다.
3. **빈틈 ③ (`E001` 전체 vs `E002` 앞부분 공정 통제 비교 부재 — 팀원 C 분담, 합류 대기 중):**
   - `E001`과 `E002`는 학습 조건이 달라 순수 Prefix 학습 효과를 분리하는 통제 비교가 별도로 진행 중이다.

## 4. 자체 진단한 부족한 점 및 리스크 (검토 시 반드시 짚어야 할 약점 6가지)

1. **`SoftJaccard`의 4-1 vs 4-2 상충 및 원래 가설과 실제 작동 기전의 괴리**
   - `SJ_2seed_avg`는 원래 해결하려던 `pre-cue FP` (`E002` `31,989` → `SJ 2-seed` `33,765`건으로 오히려 증가)나 다중 증상 마지막 발화 Recall (`54.37% → 51.76%`로 소폭 감소)을 고친 것이 아니다.
   - 실제 4-1 상승(`+0.0233` vs `E002`, `+0.0200` vs `ENS3`)은 **초반 빈 예측률 축소(`15.15% → 8.16~9.74%`)**, **단일 증상(`67.1%`) 일치도 극대화(`0.5631 → 0.5968`)**, **`오심` 정밀도 향상(`0.307 → 0.342`)** 에서 나왔다. 반대로 `오심`·`두통` 저빈도 재현율이 내려가 단독 4-2 `Macro-F1`은 약화된다.
   - 따라서 발표나 보고에서 `"SoftJaccard가 pre-cue FP와 다중 증상 FN을 해결했다"`고 서술하면 사실과 어긋난다.

2. **`SJ`/`JM` 계열에 대한 4-2 중단 정책 OOF 불일치**
   - `ENS4_sj`, `ENS4_jm`, `ENS_rep_sj42`, `ENS_rep_jm42`의 4-2 점수는 모두 `E002`(`BCE`) 5겹 OOF로 학습한 정책과 `BCE` 기반 `fit_only_shift`를 **교차 대입**한 수치다.
   - `SJ`나 `JM` 자체의 5겹 OOF로 정책과 보정값을 새로 학습한 적은 없으며(실제로 `JM42`는 `Dev nested` 탐색에서도 변동폭이 컸음), 그 때문에 `ENS4_jm` (`0.503482`)과 `ENS4_sj` (`0.502448`)이 `ENS3 + C128_v1` (`0.507411`)보다 낮게 나왔을 가능성이 남아 있다.

3. **높은 `β=128`에서의 OOF 재생성 변동 민감도 (`~0.004` 폭)**
   - `e002_oof` 실험에서 드러났듯 `δ̂` 예측의 미세한 차이(`0.0053`)가 `β=128`과 곱해지면 경계 통화의 `19.2%`에서 중단 발화 번호가 바뀌며 `~0.004` 수준의 점수 변동이 생긴다.
   - 통화 단위 bootstrap 95% 신뢰구간(`[+0.0033, +0.0139]`)은 모델 재학습 변동까지 포함하지 않으므로, 실제 미사용 데이터에서 기대할 4-2 개선폭은 `+0.0086` 단일점이 아니라 **`+0.004 ~ +0.009` 구간**으로 보수적으로 봐야 한다.

4. **중단 신호 `value = expected_rule(cal)[1]`의 구조적 괴리 미해소**
   - `m4/halting.py`의 `value` 특징은 여전히 **보정 확률 기반 기대 Jaccard** (`top-k` 선택 가정)이고 실제 출력은 **`raw p >= 0.5`** 이다.
   - `C128_v1_nonempty` 게이트를 추가해 빈 예측 상태에서 끊기는 건수를 절반(`43 → 21`)으로 줄였지만, `value` 공식 자체를 실제 `raw >= 0.5` 출력의 기대 Jaccard로 교체해 OOF부터 재학습하는 2×2 검증은 수행하지 않았다.

5. **`Dev 2,920` 반복 사용 한계 및 `e002_oof` 보조 fold 가중치 미보존 예외**
   - 모든 손실함수 비교, 앙상블 조합 확인, `C128_v1_nonempty` 검증이 동일 `Dev 2,920` 분할 위에서 수행되어 이번 후보 기준 엄격한 미사용 독립 검증은 아직 0회다(공식 `Validation 3,640`은 이번 Gap ②·③ 작업에서 1회도 열람·평가하지 않았으며, 다만 선행 팀 브랜치 `origin/mission4-streaming`에서는 `E017`·`E025`·`E026` 3회 선행 확인 이력이 있음).
   - Gap ② 5개 실행(`precue_bce_s42`, `softjaccard_s42/s43`, `jacc_macrof1_s42/s43`)은 `final.pt`, `training_state_last.pt`, `dev_prefix.npz`, `72`시점 CPU 오프라인 추론까지 전량 외장 보관·검증했으나, `e002_oof`는 5개 fold 원확률표·설정·로그·병합표만 보관했고 **`final.pt`와 재개 상태는 원격 종료 시 삭제되어 미보존**이다(`AGENTS.md` 기준 예외 사항으로 명시 필수).

6. **코드 통합 및 팀원 과제 합류 미완**
   - 현재 개선 모델(`SJ_s42/s43`, `JM_s42/s43`)과 신규 중단 정책(`policy_fitonly_c128.json` + `nonempty` 게이트)은 아직 `tools/m4_precue_bce/`와 `artifacts_private/`에 분리되어 있으며, 공식 제출 코드인 `mission4_symptom` (`m4/bundle.py`, `m4/streaming.py`, `m4/halting.py`, `inference.py`, `pytest`)에 통합되지 않았다.
   - 팀원 C의 Step 3 (`Full vs Uniform Prefix` 통제 비교) 결과 합류 및 최종 `Validation` 1회 검증이 남아 있다(제출 기한 `2026-11-20` 기준, Colab 잔여 `47.54`유닛).

## 5. 검토 에이전트에게 요청하는 핵심 판단 항목 (Decision Checklist)

다른 에이전트가 이 문서를 검토할 때 특히 **아래 5가지 판단과 근거의 타당성**을 집중적으로 점검·판정해 주기 바란다.

### 판단 1. 최종 제출 번들 구조 — `방안 A (역할 분리형 단일 번들)` vs `방안 B (공유 단일 앙상블)`
- 공식 실행 규격(`github_review/DCC_Problem` `origin/mission4-streaming@5d7539b`: `mission4_symptom/SUBMISSION_README.md`, `mission4_symptom/inference.py`)은 `--mission 4-1`과 `--mission 4-2` 모두 단일 `--ckpt_path ckpt/mission4.pt`를 넘기지만, `[참가자 구현 영역]`인 `Predictor`는 `self.mission` (`"4-1"` 또는 `"4-2"`)을 인자로 받고 `m4/bundle.py`도 이미 `rule`(4-1)과 `halt_rule`/`halt`(4-2)를 분리 저장한다.
- **검토 요청:**
  - **방안 A (역할 분리형):** 단일 `ckpt/mission4.pt` 안에 두 역할을 함께 담아 `4-1` 호출 시 `SJ_2seed_avg` (`Dev 0.526039`), `4-2` 호출 시 `ENS3 + C128_v1_nonempty` (`Dev 0.507411`)를 실행하도록 `Predictor`/`bundle`을 확장하는 것이 규정(`COMPETITION_RULES_20261114.md`)·성능·발표 논리 측면에서 정당한가?
  - **방안 B (공유형):** 4-1과 4-2가 반드시 동일한 분류기 멤버(`self.members`)를 써야 안전하다고 판단한다면 `ENS4_sj` (`4-1=0.516301 / 4-2=0.502448`)와 `ENS4_jm` (`4-1=0.512240 / 4-2=0.503482`) 중 무엇을 택해야 하는가?

### 판단 2. 4-2 `C128_v1_nonempty` 게이트의 규정 적합성
- `v(t) + 128·δ̂(t) >= 0.5` (`min_step=5`) 조건에 **`any(raw_p >= 0.5)`** (`pred.any()`) 게이트를 추가해 빈 예측 상태의 조기 중단을 막았다(`empty_at_halt 43 → 21`, `Macro-F1 0.6124 → 0.6132`).
- **검토 요청:** 이 게이트가 *"중단 판단 기준값 0.5 고정, 미래 정보 미사용"* 규칙에 100% 부합하는지, 그리고 `empty_at_halt`가 여전히 `21`건 남는 이유(끝까지 `0.5`를 못 넘긴 뒤 `finalize` 시점이나 특정 경로에서 발생했는지)에 코드/해석 결함이 없는지 확인해 달라.

### 판단 3. `β=128` 사전 고정 채택 대 `β=256` OOF 최고점 선택
- `fit 26,280` 내부 5-fold 탐색에서 `β=256` (`0.494725`, `Dev 0.507855`)이 `β=128` (`0.494581`, `Dev 0.507411`)보다 근소하게 높았으나, 격자 상한 평탄 구간(`+0.000144`)이고 회귀 오차 증폭이 2배 커지는 점을 고려해 사전 계획값인 **`C128_v1_nonempty` (`β=128`)** 를 주 채택으로 확정했다. 이 보수적 선택이 타당한가?

### 판단 4. 잔여 Colab `47.54`유닛 사용 여부 — `jm_oof` 및 `Training 29,200` 전체 재학습
- **질문 4-1 (`jm_oof`, L4 `~2.3시간` / `~4유닛`):** 방안 A로 결정하면 불필요하다. 방안 B를 택하거나 `JM` 자체 4-2 잠재력을 확인하기 위해 `jm_oof`를 추가로 돌릴 실익이 있는가, 아니면 이 시점에서는 탐색 실험을 멈추는 것이 맞는가?
- **질문 4-2 (`29,200` 전체 재학습):** `mission4-streaming` `E016`처럼 검증된 레시피(`SJ` 2-seed)를 `Training 29,200` 전체로 다시 학습해 최종 제출 번들에 넣을지(`~2유닛`), 아니면 검증된 `fit 26,280` 가중치 그대로 제출할지 판단이 필요하다. (`29,200` 재학습 시 `fit_only_shift` OOF 정책을 그대로 얹는다면 `m4/bundle.py`의 `learned_halt_setting`이 `bundle_shift` vs `policy.logit_shift` 일치를 강제하므로 호환 처리도 함께 검토해야 한다.)

### 판단 5. `mission4_symptom` 코드 통합 시 기술적 검증 누락 점검
- `m4/bundle.py:57`의 `shared_pos_weight()`는 번들 내 모든 멤버의 `pos_weight` 일치를 검사하고, `m4/bundle.py:101`의 `learned_halt_setting()`은 정책의 `logit_shift`와 번들의 `logit_shift` 일치를 검사한다.
- 방안 A(역할 분리)든 `ENS4`든, 기존 `E001`/`E002`/`E007` (`fit 26,280` vs `29,200`)과 `SJ`/`JM` (`fit 26,280`) 및 `fit_only_shift` 정책을 `pack_bundle`로 묶을 때 **단 한 군데도 불일치 오류나 잘못된 보정 대입이 생기지 않는지** 통합 설계를 검토해 달라.
